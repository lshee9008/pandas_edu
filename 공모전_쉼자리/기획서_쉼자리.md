# 쉼자리 — 말로 묻고 지도가 답하는 쉼터 입지 결정 AI

### 부제 : 주소가 아는 것으로 예산을 겨눈다

**2026년 주소정보 활용 대국민 공모전 / 서비스 개발 분야**
*(분야 표기는 공모 안내문 최종 확인 후 확정)*

---

## 0. 한 문장

> 지금까지 입지 결정은 **"어디에 지을까"** 를 물었다.
> 쉼자리는 **"3억을 쓰면 갈 수 없던 몇 세대가 갈 수 있게 되는가"** 에 답한다.
>
> 담당자는 **한국어 문장 한 줄**을 쓰고, AI는 그것을 **최적화 수식으로 번역**하며, 해는 **검증된 솔버**가 낸다.

---

## 1. 제안 요약

무더위쉼터는 전국 5만 개소가 넘는다. 그런데 2025년 온열질환자는 4,460명, 추정 사망 29명이었다. 쉼터가 부족해서가 아니다. **쉼터를 어디에 놓을지 정하는 방식이 틀렸기 때문이다.**

현재 신규 쉼터 입지는 사실상 세 가지로 정해진다 — ① 행정동별 배분, ② 시설 소유 여부(경로당·주민센터가 있으니까), ③ 민원이 들어온 곳. 어느 것도 **"거기 사는 사람이 실제로 갈 수 있는가"** 를 묻지 않는다.

「쉼자리」는 지자체 담당 공무원 전용 정책 결정 도구다. 세 가지를 바꾼다.

| 바꾸는 것 | 기존 | 쉼자리 |
|---|---|---|
| **수요를 세는 단위** | 행정동 인구 통계 | **호(戶)** — 상세주소DB의 `지하 101호`·`옥탑` |
| **도달 가능의 정의** | 직선거리 500m | **HWD** — 그늘·경사를 반영한 열노출 가중 도보시간 |
| **후보지의 정의** | 신축 부지 | **건물DB에서 추출한 전환 가능 유휴 공공건물** |

그리고 이 세 가지 위에 **여섯 개의 AI 엔진**을 얹는다. 그중 간판은 하나다.

> **NL2OPT — 정책 문장을 최적화 모델로 컴파일하는 AI.**
> "예산 3억으로, 관악구 유휴 공공건물 중에, 지하 거주 세대를 최우선으로, 다만 어느 행정동도 커버율 40% 밑으로 떨어지지 않게"
> → AI가 목적함수·제약식·가중치를 생성 → 솔버가 풀이 → 근거와 보고서 초안까지 자동 생성.

**GIS 전문가가 2주 걸려 하던 일을, 주무관이 3분 만에, 다섯 가지 예산안으로 비교해서 한다.**

## 2. 문제 정의 — 왜 지금의 입지 결정은 틀리는가

### 2-1. 네 가지 구조적 결함

| # | 결함 | 지금 일어나는 일 | 결과 |
|---|---|---|---|
| ① | **수요를 행정동으로 센다** | "○○동 65세 이상 1,200명" | 그 1,200명이 어느 층에 사는지 모른다. 반지하 85세와 신축 아파트 65세가 같은 1명이다 |
| ② | **도달을 직선거리로 판정한다** | 반경 500m 원을 그린다 | 그늘 없는 오르막 400m가 '커버됨'으로 집계된다. **못 가는 곳이 통계에서 사라진다** |
| ③ | **후보지를 갖고 있는 시설로 한정한다** | 경로당·주민센터에 지정 | 정작 사각지대에는 그 시설이 없다. 있는 곳에 또 생긴다 |
| ④ | **효과를 사후에도 측정하지 않는다** | 개소 수로 실적 보고 | "몇 개 늘렸다"는 알지만 **"몇 세대가 갈 수 있게 됐다"** 는 아무도 모른다 |

①②는 **커버리지를 과대 계상**한다. ③은 **사각지대를 고착**시킨다. ④는 **틀렸다는 사실조차 확인되지 않게** 만든다.

### 2-2. 근거 ① — 행정구역은 위험의 단위가 아니다

기상자료개방포털 전국 ASOS 관측지점의 폭염일수를 2016–2025년 집계했다(첨부 노트북에서 재현 가능).

| 지표 | 값 |
|---|---|
| 관측지점 3곳 이상인 10개 시·도의 **내부 격차 평균** | **18.3일** |
| 최대 — 경상북도 (같은 도 안에서 1.0일 ~ 35.0일) | **34.0일** |
| 전국 지점 표준편차 → 시·도 내부 표준편차 | 8.6일 → 6.6일 (**24%만 감소**) |
| 폭염일수 ↔ 열대야일수 상관계수 | **-0.01 (무관)** |
| 폭염·한파 이중노출 지점 | 86개 중 **23개 (27%)** |

시·도로 묶어도 편차의 **76%가 그대로 남는다.** 행정구역 단위 배분은 위험이 아니라 행정 편의를 따르는 배분이다.

### 2-3. 근거 ② — 누가 취약한지를 국가가 세대 단위로 모른다

- 서울연구원 「서울시 반지하주택 유형과 침수위험 해소방안」은 **건축물대장만으로 주거용 지하층을 식별하고 호수를 정확히 계산하는 것은 사실상 불가능**하다고 명시한다. 현행 반지하 통계는 **개략적 추정치**다.
- 등록센서스 방식의 반지하·옥탑 통계는 **2024년에야 최초 공표**되었고, 그마저 연 1회·행정구역 단위다.
- 복지 등록 명부는 **등록하지 않은 사람을 존재하지 않는 것**으로 만든다.

### 2-4. 그런데 상세주소DB는 이미 알고 있다

행정안전부 상세주소 부여 제도는 2가구 이상 거주 원룸·다가구·단독주택에 **동·층·호를 부여**한다. `지하 1층 101호`, `옥탑`이 이미 구조화된 데이터로 존재한다.

> **건축물대장이 못 하는 일을 주소가 이미 하고 있다. 아무도 입지 결정에 쓰지 않을 뿐이다.**

이것이 이 제안의 출발점이다. 새 조사를 하자는 것이 아니라, **이미 만들어 둔 주소 데이터를 예산 결정에 쓰자**는 것이다.

## 4. AI 엔진 — 무엇이 파격인가

여섯 개 엔진이 있다. 하나씩 보면 각각 기존 기술이지만, **입지 결정이라는 하나의 의사결정에 직렬로 물린 사례는 없다.**

---

### ① SHADE-NET — 태양을 계산해서 도로망을 다시 그린다

**"500m 이내"가 아니라 "오후 2시에 그늘로 걸어서 8분"**

건물DB의 **층수**로 높이를 추정하고, 해당 위경도·날짜·시각의 **태양 고도각·방위각**을 계산해, 건물 폴리곤을 그림자 방향으로 투영한다. 그 그림자와 보행망을 교차시키면 **구간별 그늘 비율**이 나온다.

```
그림자 길이 L = 건물높이 h / tan(태양고도각 α)
그림자 방향   = 태양방위각 β + 180°
구간 그늘비율 s_e = (그림자 ∩ 도로구간 길이) / (도로구간 길이)

열노출계수 λ_e = 1 + κ(1 − s_e)          지하·실내 연결구간은 0.3
보행부담계수 μ_e = f(경사, 계단, 횡단대기)   DEM 기반 경사도
────────────────────────────────────────────
HWD(i,j) = min over paths  Σ ( 구간거리 × λ_e × μ_e )
```

**왜 파격인가**
- 같은 400m라도 **정오의 남향 대로**와 **건물 그림자가 덮인 이면도로**의 값이 다르다
- **시각별로 도달권이 바뀐다.** 오전 10시 지도와 오후 2시 지도가 다르게 그려진다 — 이 화면 하나가 데모의 절정이다
- 겨울에는 계수만 뒤집는다: 열노출 → **체감풍속**(건물 배치 기반 풍하지대), 쿨링루트 → 웜루트. **같은 엔진으로 사계절**

**직선거리 지도와 HWD 지도를 나란히 놓으면, 그 차이가 곧 "지금까지 커버된다고 착각해 온 구역"이다.**

### ② HOUSEHOLD-RISK — 주소로 취약세대를 발굴한다

수요 가중치 w_i 를 행정동 인구가 아니라 **호 단위**로 만든다.

| 층위 | 신호 | 출처 |
|---|---|---|
| 거주 층 | 지하·반지하·옥탑 여부 | **상세주소DB** |
| 건물 | 사용승인연도, 층수, 구조, 용도 | **도로명주소 건물DB** |
| 접근성 | 승강기 유무, 진입 계단, 경사 | 건물DB + DEM |
| 밀집 | 동일 건물 세대수, 필지 밀도 | 상세주소DB 집계 |
| 노출 | 격자예보·열대야 지속일수 | 기상청 |

**2단 설계 — 정직하게 나눈다.**

- **MVP(1단계)** : 위 신호의 **가중 규칙 기반 스코어**. 가중치는 문헌(온열질환 위험요인)과 담당자 조정 가능한 슬라이더로 노출한다. 블랙박스가 아니라는 점이 행정에서는 장점이다.
- **정식(2단계)** : **PU 러닝(Positive-Unlabeled Learning)** 으로 격상. 온열질환 119 신고 지오코딩 주소를 **positive**, 나머지 전체 세대를 **unlabeled**로 두고 Elkan–Noto 보정으로 성향점수를 추정한다.
  → **"신고가 없었던 곳"을 "안전한 곳"으로 오독하지 않는 학습 구조.** 취약계층 정책에서 이 구분은 결정적이다. 도움을 요청하지 못한 사람이 통계에서 안전하게 보이는 문제를, 모델 구조로 방어한다.

> 취약계층을 **찾아 등록하는** 방식에서 → **주소가 이미 아는 것을 쓰는** 방식으로.

### ③ NL2OPT — 정책 문장을 최적화 수식으로 컴파일한다 ★ 간판

**이 서비스가 다른 모든 입지분석 도구와 갈라지는 지점.**

기존 GIS 입지분석(ArcGIS Location-Allocation 등)은 **기능이 없어서** 안 쓰이는 게 아니다. **쓸 줄 아는 사람이 부서에 없어서** 안 쓰인다. 목적함수·임피던스·시설 수를 GIS 용어로 설정할 수 있는 주무관은 드물다.

쉼자리는 그 벽을 없앤다.

```
[담당자 입력]
"예산 3억으로, 관악구 유휴 공공건물 중에서, 지하 거주 세대를 두 배로 치고,
 어느 행정동도 커버율 40% 아래로 떨어지지 않게 골라줘.
 아, 승강기 없는 3층 이상 건물은 빼고."
                              │
                              ▼
[AI 컴파일 결과 — 담당자에게 그대로 보여준다]

  집합   I = 수요 호(戶) 단위,  J = 전환가능 유휴 공공건물 후보
  변수   x_j ∈{0,1} 설치 여부,  y_i ∈{0,1} 커버 여부
  목적   max  Σ_i w_i · y_i          w_i : 지하세대 가중 ×2.0
  제약   y_i ≤ Σ_j a_ij · x_j        a_ij = 1 if HWD(i,j) ≤ 10분
         Σ_j c_j · x_j ≤ 300,000,000  (전환비용 = 연면적×단가+냉방설비)
         ∀d ∈ 행정동 :  Σ_{i∈d} w_i y_i / Σ_{i∈d} w_i ≥ 0.40
         x_j = 0  for  j ∈ {승강기없음 ∧ 층수≥3}
                              │
                              ▼
[검증된 솔버(OR-Tools CP-SAT)가 해를 계산] → 지도 + 순위표 + 근거
```

**AI 책임 분리 원칙 — 공공기관 도입의 전제**

> **LLM은 해(解)를 만들지 않는다. 문제(問題)만 만든다.**

| 담당 | 주체 | 검증 방법 |
|---|---|---|
| 정책 문장 → 최적화 스펙(JSON) | LLM (구조화 출력) | **담당자가 수식을 눈으로 확인 후 승인** |
| 스펙 → 최적해 | OR-Tools 솔버 | 수학적으로 결정적·재현 가능 |
| 해 → 설명 문장 | LLM | 수치는 솔버 출력만 인용 (생성 금지) |

이 분리 덕분에 **환각이 예산 결정에 개입할 경로가 구조적으로 차단된다.** "AI가 정했다"가 아니라 **"AI가 세운 식을 사람이 승인하고 솔버가 풀었다"** — 감사와 의회 답변에 그대로 쓸 수 있는 형태다.

**추가로 지원하는 문장 유형**
- `"작년에 온열질환 신고가 많았던 순으로 다시 정렬해줘"` → 목적함수 교체
- `"3억이 아니라 5억이면 뭐가 달라져?"` → 예산 스윕 재실행
- `"이 건물은 소유주 협의가 안 돼. 빼고 다시."` → 제약 추가 후 재해
- `"왜 A동은 하나도 안 뽑혔어?"` → 쌍대변수(shadow price) 기반 설명

---

### ④ TWIN — 반사실 시뮬레이터 : "여기 놓으면 어떻게 되는데?"

지도에서 **아무 건물이나 클릭**하면 그 자리에 쉼터를 놓았을 때를 즉시 재계산한다.

```
[클릭: ○○로 25 구 동사무소]

  신규 커버 세대       +312 세대
  그중 지하·옥탑        +87 세대
  평균 도달시간 감소     14.2분 → 9.6분  (−4.6분)
  전환 추정비용         6,800만원
  ─────────────────────────────────
  세대당 비용          21.8만원   ← 후보 12곳 중 3위
```

**그리고 여기서 결정타 — 한계효용 곡선**

쉼터를 1개, 2개, 3개… 늘려갈 때 커버 세대 증가분을 그린다. 곡선은 반드시 꺾인다. 그 **체감점(knee point)을 자동으로 탐지**해서 이렇게 말한다.

> **"4개소까지는 1개소당 평균 280세대를 새로 커버합니다.
> 5개소부터는 41세대로 떨어집니다. 예산 배분의 효율 경계는 4개소입니다."**

이것은 지도가 아니라 **예산 심의 문장**이다. 지금까지 어떤 지자체도 "쉼터를 몇 개 지어야 하는가"에 이런 근거를 대지 못했다.

---

### ⑤ PARETO — AI가 정답을 정하지 않는다, 선택지를 준다

커버리지 최대화만 하면 **인구 밀집지만 계속 뽑힌다.** 저밀도 지역은 영구히 배제된다. 이것은 알고리즘의 버그가 아니라 목적함수의 정직한 귀결이며, **공공 정책에서는 그대로 두면 안 되는 결과**다.

쉼자리는 두 개의 최적해를 **나란히** 낸다.

| | **효율 우선** (MCLP) | **형평 우선** (p-center) |
|---|---|---|
| 목적 | 총 커버 세대 최대 | 가장 열악한 세대의 도달시간 최소 |
| 총 커버 | 2,140세대 | 1,780세대 |
| 최악 세대 도달시간 | 38분 | 21분 |
| 행정동 최저 커버율 | 12% | 44% |

그리고 그 사이의 **파레토 프론트**를 슬라이더로 탐색하게 한다. 담당자가 값을 고르고, **그 선택이 기록된다.**

> **AI가 형평성을 결정하지 않는다. 형평성이 얼마나 비싼지를 숫자로 보여주고, 선택과 책임은 사람에게 남긴다.** 공공 AI가 지켜야 할 선이 여기다.

---

### ⑥ BRIEF — 선정 근거와 보고서를 자동으로 쓴다

실무에서 도구가 안 쓰이는 진짜 이유는 **결과를 보고서로 옮기는 일이 또 하루**이기 때문이다.

- **왜 이 건물인가** — 기여도 분해(SHAP 방식)로 `지하세대 밀집(41%) + 기존쉼터 공백(33%) + 전환비용 낮음(18%) + 경사 완만(8%)` 처럼 제시
- **왜 저 건물은 아닌가** — 탈락 사유를 제약식 위반 항목으로 명시 (감사·민원 대응에 직결)
- **보고서 초안 자동 생성** — 사업 개요 / 현황 분석 / 대안 비교 / 선정 근거 / 예산 산출 / 기대효과. 표·지도 이미지 포함, HWP 붙여넣기 가능한 형태
- **의회 예상질문 대응 카드** — "왜 우리 동은 빠졌나"에 대한 데이터 기반 답변 자동 생성

## 5. 기존 방식과 무엇이 다른가

| 항목 | 기존 GIS 입지분석 | 기존 쉼터 안내 앱 | **쉼자리** |
|---|---|---|---|
| 수요 단위 | 행정동·격자 인구 | — | **호(戶) 단위 취약도** |
| 도달 정의 | 직선/도로 네트워크 거리 | 직선거리 | **그늘·경사 가중 HWD (시각별)** |
| 후보지 | 분석가가 수동 지정 | — | **건물DB 기반 전환가능 유휴 공공건물 자동 추출** |
| 사용자 | GIS 전문 인력 | 시민 | **담당 주무관 (자연어)** |
| 형평성 | 목적함수에 없음 | — | **파레토 선택지 + 최소커버율 제약** |
| 산출물 | 지도 레이어 | 목록 | **예산 시나리오 + 근거 + 보고서 초안** |
| 사후검증 | 없음 | 없음 | **과거재현 백테스트 내장** |
| 계절 | 단일 | 여름/겨울 별도 | **계수 반전으로 사계절 단일 엔진** |

**"AI로 입지를 추천한다"는 제안은 이미 여럿 있다. 쉼자리의 주장은 다르다 — 추천을 잘하는 것이 아니라, 추천을 담당자가 직접 만들고 검증하고 결재까지 올릴 수 있게 하는 것이다.**


**기존에는 이 과정이 최소 2주였고, 대부분은 시작조차 되지 않았다.**

## 8. 검증 설계 — "될 것 같다"가 아니라 "맞았는지 확인한다"

입지 추천 도구는 대부분 검증되지 않는다. 쉼자리는 검증 구조를 **처음부터 내장**한다.

### 8-1. 과거재현 백테스트 (핵심 검증)

```
① 2020년 시점 데이터만으로 모델 실행 → "이때 쉼터를 여기 놓았어야 한다" N곳 산출
② 2021~2025년에 실제로 지자체가 설치한 위치와 비교
③ 두 배치안 각각에 대해, 2021~2025년 실제 온열질환 발생 분포로 커버율 평가
─────────────────────────────────────────────
결론 형태 : "AI 추천 배치는 실제 배치보다 취약세대 커버를 X% 더 확보했을 것"
```

**과거 데이터로 미래를 맞혔는지 확인할 수 있는 유일한 방법이고, 공공기관 도입 설득의 핵심 근거다.**

### 8-2. 보조 검증

| 검증 | 방법 | 판단 기준 |
|---|---|---|
| HWD의 타당성 | 온열질환 신고 지점이 HWD 사각지대에 집중되는지 | AUC ≥ 0.7 |
| 직선거리 대비 | 두 방식의 사각지대 집합 차이 | 신규 발견 세대 수 |
| 취약도 스코어 | 상위 10% 세대의 실제 신고 포착률 | Lift ≥ 2.0 |
| 솔버 재현성 | 동일 입력 → 동일 해 | 100% |
| NL2OPT 정확도 | 정책 문장 50건 → 수식 변환 정확도 (전문가 채점) | ≥ 90%, 오류는 승인 단계에서 차단 |

## 9. 활용 주소정보 — 없으면 성립하지 않는다

| 주소정보 | 쉼자리에서의 역할 | 빠지면 |
|---|---|---|
| **상세주소DB** (동·층·호) | 수요 가중치 w_i — 지하·옥탑 세대 식별 | 누가 지하에 사는지 모른다. **행정동 인구로 후퇴** |
| **건물DB** (용도·층수·연면적·승인일) | 후보지 J 자동 추출 + 그림자 높이 h | 후보지를 손으로 찍어야 한다 |
| **도로명주소 전자지도** (건물 폴리곤·보행망) | SHADE-NET 그림자 교차, HWD 경로 | 그늘 계산이 불가능하다 |
| **사물주소** | 쉼터 진입점 표기 — 좌표가 아니라 입구 | 고령자가 도착해도 못 찾는다 |
| **국가지점번호** | 논밭·실외작업장(온열질환의 44.3%) 확장 | 주소 없는 구역을 못 다룬다 |
| **주소정보시설** | 도로명판에 온습도 센서 → 골목 단위 실측 | 시·군당 관측점 1곳의 한계가 남는다 |

**어느 하나도 다른 데이터로 대체되지 않는다.** 특히 상세주소DB는 **이 서비스의 존재 이유**다 — 층·호 정보가 없으면 쉼자리는 그냥 또 하나의 GIS 도구가 된다.

**그리고 되돌려준다** — 후보지 검토 과정에서 발견되는 건물DB 오류(용도 불일치, 층수 오기), 지오코딩 실패 주소, 미부여 상세주소 구역을 **품질 개선 리스트로 자동 산출**해 주소정보 관리기관에 회신한다. 데이터를 쓰기만 하는 서비스가 아니다.

## 10. 기대효과

| 구분 | 내용 |
|---|---|
| **예산 효율** | 개소 수 기준 배분 → **세대당 비용 기준 배분.** 한계효용 체감점으로 과잉·과소 투자를 사전 차단 |
| **사각지대 재정의** | 직선거리로는 커버되는데 실제로는 못 가는 구역이 **처음으로 통계에 잡힌다** |
| **미등록 취약세대 포착** | 복지 등록 여부와 무관하게 상세주소만으로 대상 식별 |
| **의사결정 기록화** | 효율/형평 선택과 근거가 자동 기록 → **감사·의회 대응 자산** |
| **실무 채택 가능성** | GIS 전문 인력 없이 주무관이 직접 운용. 보고서 초안까지 자동 |
| **사계절·타 시설 확장** | 계수 반전으로 한파쉼터, 목적함수 교체로 **AED·대피소·스마트쉼터·그늘막·어린이보호구역**까지 동일 엔진 |
| **주소정보의 위상 전환** | 주소를 '찾아가는 수단'에서 **'예산을 겨누는 기준자'** 로 격상 |

**확장의 폭이 이 제안의 숨은 가치다.** 쉼터 입지를 푸는 엔진은, 목적함수만 바꾸면 **공공시설 입지 결정 일반**에 그대로 적용된다.

실제 도입을 전제로 미리 정리한다.

| 쟁점 | 대응 |
|---|---|
| **개인정보** | 상세주소DB는 **주소 체계 정보이지 거주자 정보가 아니다.** 개인 식별정보는 일절 사용하지 않으며, 산출물은 건물·호 단위 집계로만 표출. 필요 시 소수 세대 구역은 k-익명성 적용 |
| **폐쇄망** | Streamlit 단독 실행 패키지 제공. LLM은 (a) 외부 API (b) **온프레미스 sLLM** 선택 가능. NL2OPT가 막혀도 **폼 기반 파라미터 입력으로 전 기능 사용 가능**하도록 설계 — AI는 편의 계층이지 필수 의존이 아니다 |
| **감사 대응** | 모든 실행이 `입력 문장 → 생성 수식 → 승인자 → 솔버 버전 → 해 → 산출물` 로 로그화. 재실행 시 동일 결과 보장 |
| **책임 소재** | AI는 대안을 제시하고 **선택은 담당자가 한다.** 승인 단계 없이는 결과가 생성되지 않는 워크플로 |
| **예산** | 오픈소스 솔버·오픈 데이터 기반. 신규 데이터 구축 비용 없음. 기존 주소정보 사업 산출물에 얹는 구조 |
| **기존 시스템** | 국가주소정보시스템·재난안전시스템과 API 연계 가능. 독립 운용도 가능 |

## 부록. 한 문단 요약 (발표심사용)

> 무더위쉼터는 전국에 5만 개가 넘는데도 작년에 4,460명이 쓰러졌습니다. 부족해서가 아니라, **어디에 지을지 정하는 방식이 행정동 인구와 직선거리에 머물러 있기 때문**입니다. 쉼자리는 수요를 **상세주소의 호(戶) 단위**로 세고, 도달 가능을 **그늘과 경사를 계산한 도보시간**으로 판정하며, 후보지를 **건물DB의 유휴 공공건물**에서 뽑습니다. 그리고 담당 주무관이 **한국어 한 줄**을 쓰면 AI가 그것을 최적화 수식으로 번역하고, 검증된 솔버가 답을 냅니다. **AI는 문제를 만들고, 해는 솔버가 내고, 선택은 사람이 합니다.** 결과는 지도가 아니라 예산 문장입니다 — *"4개소까지는 1곳당 280세대, 5개소부터는 41세대. 효율 경계는 4개소입니다."* 주소가 이미 아는 것으로, 예산을 겨눕니다.
